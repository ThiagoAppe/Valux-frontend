# Informe: inicio de sesión con Google

Fecha de revisión: 17 de octubre de 2026.

## Resumen ejecutivo

La pantalla de perfil ya tiene el lugar correcto para ofrecer el acceso con Google, pero la integración todavía no existe. El botón de `profileMain.jsx` está deshabilitado, muestra el texto “próximamente” y no tiene controlador. Tampoco hay endpoints OAuth, configuración de Google, dependencias OAuth ni un modelo de datos para relacionar una cuenta interna con una identidad externa.

La alternativa recomendada para esta aplicación es **OpenID Connect de Google con Authorization Code Flow gestionado por el backend**. El navegador sólo redirecciona al backend y Google vuelve a un callback del backend. Allí se valida la identidad, se inicia la sesión JWT existente en la cookie `HttpOnly` y se redirecciona al frontend. Así, el secreto de cliente de Google no llega al navegador y se conserva el mecanismo actual de sesión única.

## Estado comprobado

| Área | Estado actual | Implicación |
| --- | --- | --- |
| Botón de Google | Existe en `profileMain.jsx`, pero tiene `disabled` y no ejecuta una acción. | No se puede iniciar el flujo. |
| Frontend | `AuthProvider` sólo conoce login y registro por email/contraseña. | Falta una acción de inicio OAuth y la lectura del resultado al volver. |
| API | Sólo existen `/auth/register`, `/auth/login`, `/auth/logout` y `/auth/me` para autenticación. | Faltan endpoints para comenzar y recibir el callback OAuth. |
| Sesión | La API emite un JWT en cookie `HttpOnly` y controla una sesión activa mediante `last_token_jti`. | Puede reutilizarse después de validar Google; no hace falta crear otra clase de cookie. |
| Base de datos | `users.password_hash` es obligatorio; no hay identidad externa. | Un usuario que sólo usa Google no puede representarse correctamente sin un cambio de esquema o un hash ficticio. |
| Configuración | No hay `GOOGLE_*` en `Backend/.env.example` ni en `config/settings.py`. | No hay cliente OAuth configurado. |
| Dependencias | No hay biblioteca OAuth/validación de tokens de Google en `Backend/requirements.txt`. | El backend no puede intercambiar ni verificar el resultado de Google de forma segura. |

La documentación existente de autenticación (`Backend/docs/auth_implementation.md`) también declara explícitamente que Google Sign-In quedó fuera de la fase implementada.

## Qué se debe crear fuera del repositorio

En Google Cloud Console:

1. Crear o seleccionar un proyecto de Google Cloud para Valux Deco.
2. Configurar la pantalla de consentimiento OAuth. Para un entorno de pruebas, agregar las cuentas autorizadas como *test users*. Para producción, completar los datos de marca, dominio y publicación que solicite Google.
3. Crear una credencial OAuth 2.0 de tipo **Aplicación web**.
4. Registrar las URI de redirección exactas del backend, por ejemplo:

   ```text
   http://localhost:8000/auth/google/callback
   https://api.example.com/auth/google/callback
   ```

   Google exige coincidencia exacta; no usar comodines ni la URL del frontend como callback.
5. Solicitar únicamente los scopes `openid`, `email` y `profile`.
6. Conservar el **Client ID** y el **Client Secret** generados. El secreto se guarda sólo en el gestor de secretos o en `Backend/.env`; jamás en Vite, código frontend ni Git.

Para el flujo recomendado, no es necesario exponer el Client ID al frontend: el backend construye la URL de autorización. Si más adelante se elige Google Identity Services en el navegador, sí haría falta `VITE_GOOGLE_CLIENT_ID`, pero esa es una arquitectura distinta y no debe mezclarse con ésta.

## Configuración y dependencias a agregar

Extender `Backend/config/settings.py` y `Backend/.env.example` con valores sin secretos reales:

```env
GOOGLE_OAUTH_CLIENT_ID=
GOOGLE_OAUTH_CLIENT_SECRET=
GOOGLE_OAUTH_REDIRECT_URI=http://localhost:8000/auth/google/callback
```

También se debe declarar una biblioteca OAuth/OpenID Connect que permita intercambiar el código y validar el ID token. Una opción concreta es `Authlib`; si la implementación usa un cliente HTTP separado, agregar además `httpx`. Se debe actualizar el archivo de dependencias canónico que se use para desplegar (`Backend/requirements.txt`) y mantener alineado el archivo histórico `Backend/requierements.txt`, hoy un archivo de compatibilidad.

En producción, `FRONTEND_BASE_URL`, `CORS_ORIGINS`, `AUTH_COOKIE_SECURE=true` y `AUTH_COOKIE_SAMESITE` deben configurarse según el dominio HTTPS real. Si frontend y API están en sitios distintos, `SameSite=None` exige `Secure=true`.

## Cambio de datos necesario

Se recomienda crear una tabla de identidades externas mediante un nuevo script SQL versionado en `Enviroment/Database/schema_changes/`; la aplicación no debe alterar la base automáticamente.

Modelo mínimo propuesto:

```sql
CREATE TABLE external_identities (
  id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  provider VARCHAR NOT NULL,
  provider_subject VARCHAR NOT NULL,
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL,
  UNIQUE (provider, provider_subject),
  UNIQUE (user_id, provider)
);
```

- `provider` tendría inicialmente el valor `google`.
- `provider_subject` debe ser el `sub` validado del ID token; no el email, porque este puede cambiar.
- No guardar access tokens, refresh tokens ni el ID token salvo que exista una necesidad concreta y un diseño de cifrado, rotación y revocación.

Además, `users.password_hash` debe admitir `NULL` para las cuentas creadas exclusivamente con Google. En consecuencia, el login por contraseña debe tratar un hash nulo como credenciales no válidas sin intentar verificarlo. Usar un hash aleatorio ficticio para sortear la restricción `NOT NULL` oculta el modelo real y complica una futura recuperación de contraseña.

Agregar el modelo ORM de identidad, sus relaciones con `User` y su importación en `database/models/__init__.py`.

## Política de cuentas a decidir antes de implementarla

Hay que definir cómo resolver una identidad Google cuyo email ya pertenece a un usuario local. La recomendación es **no vincularla automáticamente sólo por coincidir el email**. En ese caso, responder con un estado claro y pedir que la persona inicie sesión con su método existente; desde una sesión autenticada se podrá ofrecer “Vincular Google”.

Esta política evita fusionar cuentas por una regla implícita. Si se decide vincular por email verificado, debe quedar explícito, requerir que la claim `email_verified` sea verdadera y cubrir el caso de una identidad ya vinculada a otra cuenta. La decisión cambia la experiencia y las pruebas, por lo que no conviene asumirla durante la implementación.

## Backend a implementar

1. Agregar la configuración validada de Google al objeto `Settings`. La aplicación debe fallar al arrancar cuando se habilite OAuth sin Client ID, Client Secret o redirect URI completos.
2. Crear `GET /auth/google/login`:
   - recibe opcionalmente un destino interno `returnTo`;
   - valida que sea una ruta local (empieza con `/` y no con `//`), como ya lo hace la pantalla de perfil;
   - genera `state` criptográficamente aleatorio y `nonce`;
   - conserva ambos, junto con el destino, con vencimiento corto y uso único;
   - redirecciona a la autorización de Google con los scopes mínimos.
3. Crear `GET /auth/google/callback`:
   - valida `state` y su vencimiento antes de usar el código;
   - intercambia el `code` en el servidor usando el Client Secret;
   - valida criptográficamente el ID token, incluyendo firma, `iss`, `aud`, `exp`, `nonce` y `email_verified`;
   - busca la identidad por `(provider, provider_subject)`;
   - crea el `User`, `Customer` e identidad externa en una transacción sólo si no existe y la política de email lo permite;
   - reutiliza `start_session()` para generar el JWT y la cookie actuales;
   - redirecciona a `settings.frontend_url("/perfil")` o al `returnTo` previamente validado.
4. Crear un servicio dedicado, por ejemplo `GoogleAuthService` o ampliar `AuthService`, para que el router no concentre el intercambio de código, consultas y decisiones de alta/vinculación.
5. Añadir el endpoint protegido de vinculación si se adopta la política recomendada. Debe iniciar un flujo Google separado, ligado al usuario actual, y rechazar identidades que pertenezcan a otra cuenta.
6. Definir respuestas de error seguras: nunca devolver tokens, secretos o detalles de la validación. Redireccionar al perfil con un código de error breve que el frontend traduzca a un mensaje en español.

El `state` no debe vivir en una variable global de proceso: se perdería al reiniciar o al escalar la API. Puede guardarse temporalmente en una tabla de base de datos, Redis u otro almacenamiento compartido. El mecanismo elegido debe permitir consumo único y expiración.

## Frontend a implementar

1. En `Frontend/src/services/authService.jsx`, agregar una función que forme la URL de `/auth/google/login` a partir de `API_BASE` y redireccione el navegador con `window.location.assign(...)`. No usar `fetch`: una autorización OAuth necesita navegación de página completa.
2. Exponer esa función como `loginWithGoogle` desde `AuthProvider`.
3. En `AuthenticationForm` de `profileMain.jsx`:
   - reemplazar el botón deshabilitado por un botón activo;
   - ejecutar `loginWithGoogle(returnTo)`;
   - mostrar estado “Redirigiendo a Google…” y prevenir dobles clics;
   - mantener el marcador `GoogleMark` actual y el texto en español;
   - convertir el error devuelto al volver en un mensaje accesible con `role="alert"`.
4. Al volver al frontend, `AuthProvider` ya ejecuta `GET /auth/me` al montar y cargará la sesión creada en el callback. Si el proveedor redirige a la SPA sin recargarla en algún caso, invocar explícitamente una función de recarga de sesión en el contexto.
5. No persistir tokens de Google ni JWT en `localStorage`, URL, estado global persistente o logs del navegador.

## Secuencia esperada

```text
/perfil → botón Google → GET API /auth/google/login
         → Google (consentimiento)
         → GET API /auth/google/callback?code=...&state=...
         → valida token / crea o encuentra usuario / emite cookie HttpOnly
         → redirección a /perfil o returnTo
         → GET /auth/me → perfil autenticado
```

## Pruebas y criterios de aceptación

Antes de liberar, verificar como mínimo:

1. Usuario Google nuevo: se crea un `users`, `customers` e `external_identities` asociados, y se llega autenticado al perfil.
2. Segundo acceso de la misma cuenta: reutiliza la identidad y no duplica registros.
3. Inicio por contraseña de un usuario Google sin contraseña: responde como credenciales inválidas y no produce error interno.
4. Email repetido entre cuentas locales y Google: sigue exactamente la política que se decida; nunca une registros silenciosamente.
5. `state` alterado, repetido o vencido: no inicia sesión.
6. ID token con audiencia, emisor, firma, nonce o expiración inválidos: no inicia sesión.
7. Un `returnTo` externo como `https://otro-sitio.example` o `//otro-sitio` nunca genera una redirección externa.
8. Logout revoca la sesión Google igual que una sesión local y elimina la cookie.
9. Iniciar una nueva sesión conserva la regla actual de una única sesión activa.
10. `npm run lint` y `npm run build` pasan en `Frontend/`; además, probar el callback con la URL registrada en Google y la base local configurada.

## Orden recomendado de trabajo

1. Definir la política de vinculación por email y los dominios de desarrollo / producción.
2. Crear las credenciales Google y cargar los secretos sólo en el entorno correspondiente.
3. Preparar y revisar el script de esquema y el modelo ORM.
4. Implementar configuración, servicio OAuth y endpoints de backend.
5. Conectar el botón y la gestión de estados/errores del frontend.
6. Ejecutar las pruebas manuales anteriores y revisar cookies, CORS y HTTPS en producción.

## Fuera de alcance de esta primera integración

- Sincronizar foto, nombre o contactos de Google en cada inicio de sesión.
- Solicitar permisos de Drive, Calendar, Gmail u otros datos no necesarios.
- Recuperación de contraseña o conversión automática de una cuenta Google en una cuenta con contraseña.
- Almacenar refresh tokens o realizar llamadas a APIs de Google en nombre del usuario.
